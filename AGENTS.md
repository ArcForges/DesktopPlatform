# DesktopPlatform contributor instructions

This repository owns shared desktop mechanisms, C# interop, CMake/vcpkg and capability NuGet production.
The product applications, Cloud, AI, Web, Mobile and business RPC schemas have separate repositories.
The design authority for active development is [ArcForges-Design](https://github.com/ArcForges/ArcForges-Design) ([AD-0001](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0001-flagship-pivot.md)).

- Work on a focused branch in `.worktree/`. Preserve the primary checkout and unrelated repositories.
- Use C# 14 / .NET 10 from `global.json`, C++20 and C17-compatible public C ABI headers.
- Keep native toolchains here. Consumers use exact published package versions and committed lock files;
  never add Git submodules or sibling source dependencies. Business proto generation belongs to Contracts.
- Put dependency versions in `Directory.Packages.props`, restore locked, retain warnings-as-errors and
  AOT/trim diagnostics. Native interop uses owned C ABI / LibraryImport, never a C++ ABI.
- Add SPDX headers to source/configuration; preserve third-party notices and source provenance.
- New projects are non-packable by default. Admit a package explicitly in `eng/packaging/packages.json`
  only when its behavior and dependency closure are verified. Never publish placeholders as capabilities.
- Keep build inputs declarative; executable packaging verification is the portable Python tool under `eng/`.
  Do not add tracked PowerShell or shell helper scripts.
- Record what actually ran. A successful package-policy smoke does not prove native capability AOT,
  product behavior, release signing or NuGet publication. Run the checks documented in the README.

## Flagship role

DesktopPlatform is an **active** repository of the ArcForges flagship ([AD-0001](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0001-flagship-pivot.md)). Per [architecture 01 §5](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/architecture/01-system-overview.md#5-repository-and-project-map) and the [reuse classification](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/reuse/inventory-and-classification.md#2-desktopplatform), it adapts `ArcForges.LocalRpc` (service-endpoint mode, stream lane, per-method limit profiles and a peer identity provider; [refactor](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/reuse/desktopplatform-refactor.md)) and `ArcForges.Security.Secrets` (Linux backends). The flagship reuses `ArcForges.Observability`, `ArcForges.DesignSystem`, `ArcForges.Desktop.Shell` and `ArcForges.Build.Policy`, and reuses `ArcForges.Persistence.Sqlite`, `ArcForges.NativeInterop`, `ArcForges.Foundation`, `ArcForges.Security` and `ArcForges.Security.Audit` where they fit. The other application-family packages, ContentSandbox and the native image packages are retained for future products and are not scheduled. The unfinished items the classification lists (Linux TSYNC, the in-repository Shell Avalonia adapter, the PLT.66 Contracts move, wrong-user procedures) are retained too and are not flagship prerequisites.

## Delivery (serial, ArcForges/Plan)

Tasks for this repository come from the [Plan delivery graph](https://github.com/ArcForges/Plan/blob/main/delivery-graph.json) and are delivered under the Plan [execution policy](https://github.com/ArcForges/Plan/blob/main/execution-policy.md) and [delivery procedure](https://github.com/ArcForges/Plan/blob/main/delivery-procedure.md) ([AD-0014](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0014-delivery-method.md)). They are binding. The historical P2-018 model (delivery lanes, adoption slices, `delivery.py` claims and handoffs, parallel workers, integration-owner roles, Plan leases, the build slot and the launcher) is retired and never resumed.

- One task is active at a time. Work only inside its write scope, in a worktree `.worktree/<task-id-lower>` on branch `task/<task-id-lower>`, never in the primary checkout.
- Delegated workers and reviewers work locally. Only the coordinator pushes (through the pre-push hook), opens pull requests, merges at the reviewed head and publishes. The merge gate is the hook's `arcforges-verify: PASS` line at the pushed head for the owner's PRs and the hosted PR gate for external PRs ([Hosted CI](#hosted-ci)).
- Title pull requests `[<TASK-ID>] <summary>`.
- Shared files: the task that adds a project, dependency or job appends it to the solution and project lists, `Directory.Packages.props` and the CI job lists; lock files are regenerated after rebase, never hand-merged. `eng/packaging/packages.json` gains one entry per admitted package, and every merge to main publishes all packages at one version. The vcpkg baseline and overlay ports change only through a dependency-admission change; generated policy data is regenerated from its pinned source; the reason-code registry is append-only.
- The design-policy, reference-baseline, runtime-ownership and reconciliation checks (`eng/design_policy.py`, `eng/reference_baselines.py`, `eng/runtime_ownership.py`, `eng/reconciliation.py`) validate against exact pinned commits of the historical design corpus, which is now the read-only `ArcForges/ArcForges-Design-Parallel` (AD-0001). The recorded identities stay `ArcForges/ArcForges-Design`; the checks fetch those commits from `ArcForges/ArcForges-Design-Parallel` through the single mapping in `eng/historical_sources.py` (ArcForges/DesktopPlatform#180). Never work around a failing check by changing pins, exports or records. Change `eng/policy/design-source.json` and both generated exports only together, through a reviewed change; see [design policy](docs/design-policy.md). Its "Reviewed refresh" procedure (repinning from a newly merged Design PR) no longer applies, because the historical corpus is frozen; the current design is `ArcForges/ArcForges-Design`, which these checks do not read.
- Earlier `docs/` records named after work packages or substeps describe their original scope; they are evidence, not execution instructions. Where older documents prefix a command with `delivery.py build-slot run … --` or assign a step to an integration owner, that is historical: run the wrapped command directly, and leave pushing and merging to the coordinator.

## Validation policy (P2-017)

The historical [CI and local validation policy](https://github.com/ArcForges/ArcForges-Design-Parallel/blob/64173614f2c41543bfff8f6df8d5a9e41207eb0a/docs/assurance/ci-and-local-validation-policy.md) (ArcForges-Design-Parallel at `64173614`) stays in force for this repository, except its rule 9 (parallel delivery), which AD-0014 supersedes. Where it differs from the Plan execution policy, the Plan governs.

- Never add or execute macOS CI, native/runtime/package-consumer execution, GUI, browser, device, live-service or published-package installation tests in any CI trigger or nested build script.
- Keep necessary Windows/Linux compilation, packaging, targeted offline unit/static checks and non-duplicated security checks. Runtime diagnostics are explicit local opt-in only for affected behavior using existing tools. The pre-push hook runs the PR gate's checks and nothing more ([Local verification](#local-verification-ad-0016)).
- Preserve locks, required signatures, licence/provenance and one identity/integrity check at each real trust handoff. Do not routinely download public artifacts or repeat archive/hash/consumer verification after publication. Narrow FFmpeg licence/configuration and Windows signature inspection remain legal admission checks.
- Do not reinstall vcpkg, SDKs or toolchains to expand validation. Do not create tags or republish solely for verification. Use the normal network and never change proxy or network configuration (no port 7890). Diagnose a failure before any rerun, retry transient failures with bounded backoff, inspect remote state before retrying a write, and report the exact operation when a failure persists. Linux checks run on the Linux MCP host, through the Linux MCP server, never through local WSL, not even as a fallback ([AD-0018](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0018-native-platforms-without-wsl-integration.md), [AD-0019](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0019-mcp-first-verification.md)); installs there are the user's, and there is no SSH.
- Record removed coverage honestly. Every pull request gets an independent review of its complete latest head; the coordinator merges only at the reviewed head after its merge gate passes ([Hosted CI](#hosted-ci)). Post-merge work stops after commit/job/publication status and a clean primary fast-forward; retain branches/worktrees.

## Local verification (AD-0016)

The owner's (`deku2026`) PRs are verified by the repository's pre-push hook, not by hosted CI ([AD-0016](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0016-local-first-verification.md)). The cross-repository rules are the Plan [AGENTS.md](https://github.com/ArcForges/Plan/blob/main/AGENTS.md) rules 6 and 7.

- **Install** once per clone, from the main checkout on `main`: `python eng/verify.py install`. It copies `.githooks/*` into the clone's common hooks directory, so every worktree runs them, and removes any `core.hooksPath`, including per-worktree values left by older scripts, and refuses while one remains elsewhere. Re-run it when `.githooks/` changes.
- **Two legs on two machines** ([AD-0018](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0018-native-platforms-without-wsl-integration.md) §5, as amended by [AD-0019](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0019-mcp-first-verification.md)). Each step runs on one host, `win` (native Windows) or `linux` (native Linux); `eng/verify.py` runs only the leg of the machine's own operating system, never through WSL or a remote shell. The Windows leg runs on the Windows 11 workstation, through the Windows MCP server; the Linux leg runs on the Linux MCP host, through the Linux MCP server. Both are standard MCP servers that Claude Code and Codex share; their client configuration and credentials stay outside this repository. Local WSL is never a venue, not even as a fallback.
- **Stop rule** (AD-0019 §5). If the Linux (or Windows) MCP server is unavailable, unreachable or its host lacks a prerequisite, stop verification and report the exact failure: the leg has no record, so the push stays rejected. Never skip, mock or weaken a step, run the leg on another host (local WSL or an agent's own sandbox included), write a record by hand, or bypass the hook. Until the Linux MCP server exists (Plan H-22), no Linux leg can be recorded, so every push is rejected; there is no transition venue (AD-0019 §8).
- `python eng/verify.py list` shows the profile, the steps and the state of each leg. `python eng/verify.py run` verifies this machine's leg of `HEAD` now and records it, keyed by the commit (the secret scan reads it), the merge base, the step set and the scripts; a local record is reused while the tool versions are unchanged. It prints `arcforges-verify: LEG PASS ...`, then `PASS` when both legs have a record, else `INCOMPLETE`.
- **Each leg on its own.** Each leg builds and verifies its own responsibilities from the commit alone, in either order: nothing a leg produces is carried to the other machine. The Windows leg produces the native stage and its licence evidence and everything that needs them (the architecture gate, the NuGet candidate and its packaging tests); the Linux leg builds, tests and checks the policies on Linux. The other machine checks out the exact commit in a worktree of its clone (a commit that is not on GitHub yet travels as a bundle: `git bundle create <file> HEAD --not origin/main` here, `git fetch <file> HEAD` and `git worktree add --detach .worktree/<key> FETCH_HEAD` there) and runs `python eng/verify.py run` there; bring its record (`leg-<host>-<key>.json`, named in the `LEG PASS` line) back and `python eng/verify.py import <record>`, which checks it against the commit here and refuses any mismatch. A push needs a passed or imported record of both legs.
- **What runs.** Each pushed commit, never the working tree, as listed in `eng/verify_steps.py`: every job of the PR gate (`pr-gate.yml` with the called `native-abi.yml` and `package-validation.yml`), each on the host the hosted job used. Every change runs the full profile (the provenance, runtime-ownership and reconciliation inventories cover Markdown too).
  - Lane `win`, in `<main checkout>/.worktree/_verify`: the locked restore; `native` (the IDE licence evaluation, `vcpkg install` of the pinned ports from `C:\vcpkg` into `artifacts/vcpkg-installed`, the `win-x64-shim-static` preset with sccache in the developer environment of the reviewed MSVC toolset, CTest, the NativeAbi layout tests, the sccache proof); `native-stage`; the seven win-x64 Native AOT compile probes; then the `pack` job (`windows-latest`) up to its tests: the naming evidence its architecture gate binds (`win-naming-evidence`, which hosted CI downloads from `runtime-policy`), the Release build and every test suite of `pack` except the architecture gate and the timing-sensitive LocalRpc suite (four test projects at a time). The installed tree, the CMake build directory and the caches persist, so a warm run rebuilds only what changed.
  - Lane `linux`, in the Linux-native clone `~/.cache/arcforges-verify/DesktopPlatform`: `clone-identity` (its `origin` URL is this GitHub repository and `origin/main` the merge base, which the policy and provenance checks read; nothing is fetched from it), the locked restore, the licence, runtime-ownership and reconciliation policies, the rest of the `linux-platform` job (`dotnet format --verify-no-changes`, the accounting and OS secret-store guard unittests, the Release build, every test suite of the `pack` job except the architecture gate and the timing-sensitive LocalRpc suite, four test projects at a time), and the six linux-x64 Native AOT compile probes.
  - Lane `linux-policy`: the design, reference-baseline and provenance policies, stage integration, the hash-pinned pre-commit hooks and the unittest of the Windows leg's native evidence layout (`native-evidence-tests`). Lane `scan`: the pinned gitleaks image over the pushed range with `.gitleaks.toml`, without network; `actionlint` when `.github/workflows/**` changed.
  - After every lane of a leg: on each leg the LocalRpc suite alone; on Windows then the rest of `pack`, from the native stage and licence evidence this leg produced: `architecture-gate` (the native licence evidence laid out where CI downloads the artifact, the architecture tests, invariant accounting and the reason registry), `pack` (the candidate at the local version `1.0.0-ci.1.1`) and the packaging unittest against it.
  - Local equivalents of GitHub-bound parts: run 1, attempt 1 instead of the run id; where a hosted job downloads another job's artifact, the same file produced on the leg's own machine. When vcpkg built the ports with a CMake other than the reviewed `vcpkgCMake` (Env.md §6: a local version difference is not a failure), the stage, pack and packaging steps pass that version as `ARCFORGES_LOCAL_NATIVE_TOOLCHAIN`: the stage's SBOM records it as `localToolchain`, every other native check stays, and the allowance is refused under GitHub Actions, so hosted CI and publication keep the reviewed toolchain. The hosted secret-scan receipt (RP-09) cannot be produced locally by design, so the architecture gate accepts exactly that finding and nothing else; the secret scan itself runs in the hook. Not reproduced: dependency review and CodeQL (GitHub services; external PRs and the weekly Deep check). `CI` is not set.
- **Prerequisites** (installs are the user's): on Windows, the .NET SDK selected by `global.json` (the user-local SDK root first on `PATH`), Python 3.14, PowerShell 7, Visual Studio with the MSVC toolset recorded in `eng/provenance/artifact-profiles/native-win-x64-r4.json` and a Windows SDK, CMake 4.3.3, Ninja 1.13.1, sccache, and `C:\vcpkg` (or `VCPKG_ROOT`) at the commit pinned in `eng/packaging/native.py`, never changed to pass the check; on the Linux host, the same .NET SDK, Python 3.14 with `venv` (`python` on PATH), Clang and lld, CMake, and Docker with the pinned gitleaks image; network access to NuGet, PyPI and GitHub.
- **Failures.** A failed, timed-out or unrunnable step, or a missing leg record, rejects the push and prints the step, the last log lines and the log path (`<git common dir>/arcforges-verify/logs/`). Read the log, fix the cause, push again.
- AI agents must never use `git push --no-verify` to bypass required validation.
- They must also never disable, remove, modify, or otherwise circumvent the hooks merely to allow a push.
- Only `python eng/verify.py import` brings in another machine's leg, and only the record that `python eng/verify.py run` wrote on that machine at the exact commit: writing, editing or reusing a pass record by hand is circumventing the hooks.
- If validation fails, investigate and fix the underlying issue.
- If a required local test cannot run, do not silently skip it or claim successful verification.
- Changing `eng/verify*.py` or `.githooks/` as reviewed engineering work is allowed; changing them to get a push through is not.

## Efficient execution

The Plan's rule 7 applies. In this repository:

- Restore once (`dotnet restore DesktopPlatform.slnx --locked-mode`), build incrementally (`dotnet build DesktopPlatform.slnx -c Release --no-restore`), then run only the affected test projects: `dotnet test --project <project> -c Release --no-build`.
- For a policy or tooling change, run its unittest (`python -m unittest discover -s eng -p test_<name>.py -v`) and the policy script; for packaging, `python -m unittest discover -s eng/packaging -p 'test_*.py' -v` after a pack.
- For native code, build the preset incrementally in the developer environment (`cmake --build --preset win-x64-shim-static`); never clear `artifacts/vcpkg-installed`, the CMake build directory or the vcpkg and sccache caches without a cause.
- Format only the changed files while iterating: `dotnet format DesktopPlatform.slnx --no-restore --include <files>`.
- The full profile runs once, through `python eng/verify.py run` before handover, so that the push reuses the pass.

## Hosted CI

- **Owner PRs:** every PR gate job is skipped (`ci` too). No required status checks exist in this repository.
- **External PRs** (Dependabot included): the full PR gate as before: dependency review and the full-history secret scan, the repository hooks, the policy jobs, the native win-x64 build, both Native AOT matrices, the managed `pack` job, and `ci`, which requires every gate.
- **Main pushes and `v*` tags:** `publish-nuget.yml` only: preflight, the candidate (the PR gate through `workflow_call`) and the publication of its bytes. The candidate re-runs the gates because the publication evidence binds them to the published bytes (a known limitation, AD-0016).
- **Manual and scheduled:** the Deep check (C# CodeQL, weekly and on dispatch) and the Native build (dispatch).
- **OS secret-store tier** (`os-secret-store-tier.yml`, AD-0016 amendment of 2026-10-17): the minimal, sequential Credential Manager tests of `tests/OsSecretStoreTests` alone, on a hosted `windows-latest` runner, for external PRs, `merge_group`, dispatch and weekly; skipped for owner PRs and pushes. Only its test step sets `ARCFORGES_OS_SECRET_STORE_TESTS=1`. Routine suites and the pre-push hook never reach a real OS secret store: every test project sets the tripwire switch `ArcForges.Security.Secrets.DenyOsStores`, `eng/verify_local.py` removes the opt-in, `eng/verify_steps.py` refuses to run with it, and `ArchitectureTests` enforce the tier's boundary. Locally the tier runs only through `python eng/os_secret_store_tier.py` on the user's explicit opt-in (Linux Secret Service only on the isolated Linux secret-store test host behind the Linux MCP server, marked by the root-owned `/etc/arcforges/isolated-secret-store-test-host`; ArcForges-Design AD-0019 §6); agents never set the opt-in or run the tier unless the user explicitly asks, and never stress or load a real OS store.

## Dependency admission (WP02.05)

- Keep `eng/policy/dependency-policy.json` bound to the complete actual dependency inputs. A dependency or framework change requires a reviewed replacement receipt, closure/licence and maintenance review and every upgrade checklist item. Hash refresh alone is insufficient.
- Preserve existing source/native provenance and public/internal import gates. Stable closures cannot import prerelease dependencies; only recorded exact foundation candidates are permitted in development.
- Framework major upgrades require explicit runtime/AOT/trim and affected Android Kotlin/JVM/ART/R8 assessment under VG-08. Record conditional local coverage honestly without adding forbidden CI or provisioning tools.
