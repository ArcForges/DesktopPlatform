# Local security audit (PLT.44)

`ArcForges.Security.Audit` owns an owner-scoped SQLite file whose security-event table is `local_audit`. It is separate from PLT.01 product content/journal storage and has no dependency on `ArcForges.Observability`; neither system queries or projects the other's records. The library reuses the already-admitted `Microsoft.Data.Sqlite` 10.0.12 closure and ships as the `ArcForges.Security.Audit` package: PLT.44 selected no package identity; PLT.46 enabled packing, listed the package in `eng/packaging/packages.json` (the repository policy test requires every packable project to be listed there) and owns its pack, publish, and consumer acceptance.

Callers select an explicit database path, realm/account owner, and finite `AuditRetentionPolicy`. The file binds its owner, retention duration, and policy ID on first creation and fails closed if a later open disagrees. Retention is divided into complete UTC calendar months. A month becomes eligible only after its last instant plus the configured retention days; there is no implicit infinite-retention default.

An `AuditEvent` has a closed event/risk/decision/reason/origin vocabulary, the complete PLT.36 `ActorChain`, executor and software identity, a canonical capability key, an opaque typed resource ID, and optional workspace/task/correlation IDs. The shape deliberately has no message, payload, arbitrary tags, paths, secret values, prompts, or document content. A caller must authorize append and query operations at its composition boundary; owner-scoped storage is not a substitute for an application access-control decision.

All appends and maintenance run through one in-process path lock and SQLite's serialized write transaction. SQLite triggers and a connection authorizer reject ordinary updates/deletes; the maintenance gate is connection-private and transaction-scoped. Purge and hold-release entry points are internal to the assembly. The dedicated policy-retention authority privately mints a nonserializable capability bound by object-reference identity to one store, policy, owner/month/action, hold (for release), and a five-minute window. Ordinary callers cannot construct, deserialize, or request this capability, and string role names are not accepted. An active hold blocks purge. Event deletion, the consumed authority-actor/software receipt, and the immutable purge receipt commit together. Receipts are durable audit evidence, not cryptographically signed approvals. The purge receipt retains the exact partition, row count, sequence coverage, SHA-256 over ordered event identities/digests, and full authority actor chain.

## Typed intakes (egress decisions and capability-lease lifecycle)

The generic `AuditStore.Append` path cannot express these facts incorrectly: `AuditEvent` enforces closed per-type shapes, so a `DataEgressAuthorized`/`DataEgressDenied` event requires typed `AuditEgressDetail`, a correlation, no typed resource reference, and an allowed/denied decision whose generic reason is the one its egress reason and authority kind map to; a capability-lease event requires the `CapabilityLease` resource kind and the decision/reason of its lifecycle kind; no other event type may carry either. `AuditRisk` mirrors the R0-R4 scale without loss, and its `NotAssessed` marker is accepted only on an egress event. Neither shape has content, secret, path or property-bag fields.

`EgressDecisionAuditAdapter.Record(EgressAuditRecord)` projects one real PLT.41 audit record (allowed or refused) and appends it synchronously, returning only after the row is committed. `CapabilityLeaseAuditAdapter.Record(CapabilityLeaseLifecycleFact)` appends one issued, revoked, expired or task-ended fact and stores `AuditCapabilityLeaseId.Value` directly as the Guid-valued resource identity (never stringified, hashed or truncated). Both let every failure propagate, so an enforcement path that calls `Record` before releasing a transfer cannot release an allowed transfer whose audit append failed. Unknown lifecycle kinds, empty identities and contradictory decision/reason pairs are refused.

`ArcForges.Security` owns the egress and lease sink ports and never references this project. **Lease lifecycle (integrated).** `CapabilityLeaseEventAuditSink` implements the PLT.43 `ILeaseEventSink` over `CapabilityLeaseAuditAdapter`, so the real `CapabilityLeaseManager` writes its issued, revoked, expired and task-ended facts to the audit store. The mapping is closed: `CapabilityLeaseId.Value` is the audit resource Guid, the event kind maps one to one, the reason comes from the lease's own issue basis or revocation reason (policy-allowed, user-approved, step-up, risk-accepted; owner-revoked becomes user-rejected, authority-lost becomes authority-missing; expiry is policy-expired; task end is not-applicable), and risk, task, workspace and origin come from the lease. The actor chain is the delegator's issuing chain (the lease snapshot does not record the revoking principal), the software identity is the issuing chain's final actor or the composition root's fallback for a direct issue, and the occurrence time is stamped by the store at append (an expiry fact written by a later sweep is stamped at the sweep, not at the expiry instant). A fact the audit shape cannot hold (a capability key that is not a canonical audit key, another owner's lease, a purged partition, a disposed store) throws, so the manager refuses the issue (`AuditUnavailable`) or reports the end fact as still owed and retries it on the next sweep. Facts are written at least once. The offline tests drive the real `CapabilityLeaseManager` against a real `AuditStore` with an in-memory lease store; they do not run any host composition root or a durable lease store.

**Egress decisions (integrated).** `EgressAuditSink` implements the PLT.41 `IEgressAuditSink` over `EgressDecisionAuditAdapter`, so the real `EgressAuthority` writes every decision that reaches its sink into the durable store before it releases the decision; an append failure throws and the authority refuses an allowed transfer with `AuditUnavailable`. The audit event is a projection of the delivered `EgressAuditRecord` (Design architecture/08 EG-06 to EG-09) and never invents a value:

- **Data class** is PLT.41's tier (public, diagnostic, workspace content, sensitive content, secret material) or the explicit `Unclassified` marker; **destination class** is PLT.41's class or the explicit `Undetermined` marker; the destination identity (the canonical origin without its scheme) is absent only for a malformed destination. A refusal before classification is therefore stored as what it is.
- **Reason** is the exact `EgressReason` (`AuditEgressReason`) beside the closed generic reason it maps to (an allowed decision follows its real authority kind: user consent is user-approved, workspace policy and product route are policy-allowed).
- **Authority** is the kind, reference and grant generation of an allowed decision; every refusal records `NoAuthority`.
- **Effective risk** is `NotAssessed`: the egress decision is pipeline step 8 and risk is assessed at step 9, and the record carries none. A supplied R0-R4 is accepted by the shape, but PLT.41 supplies none.
- **Resource**: the event has no typed resource Guid. The opaque resource id and revision (caller-bound text that can be path-like) are stored as an unsalted SHA-256 content reference fingerprint. It is a reference, not a secret: a low-entropy or path-like id can be confirmed by guessing by anyone who can read the audit file. The exact reference stays in the correlated step 14 security audit record of the same command.
- The record's occurrence time is not used; the store stamps the event. The grant issuer, allowlist generation and AI-eligibility flag are not stored. A record that contradicts itself, a non-canonical capability or destination, a foreign owner, a purged partition or a failing store throws.
- `EgressAuthority` builds an `AuditUnavailable` refusal when an allowed decision cannot be made durable but does not write it to the sink, so it has no event; a write that timed out can land later as an Authorized event beside it, which is valid and authorizes nothing. A refusal whose own audit write fails is not retried by PLT.41 and is lost.

Legal holds are append-only place/release facts with full actor chain, software identity, origin, and a typed reason. A hold ID is never reused. Hold placement authorization remains the owning application's responsibility; release and purge are additionally fenced by the configured policy-retention authority.

This protects against ordinary API/SQL roles; it does **not** make a desktop-local file tamper-proof. A person who controls the machine or database file can replace or modify that file, so callers and product copy must not claim otherwise. The library does not silently export, sync, join, or correlate audit with telemetry.

## Retention runner (production entry to purge)

`AuditRetentionRunner` is constructed with an `AuditStore`, a maintenance `ActorChain` of that store's realm and owner (another owner is refused with `UnauthorizedAccessException` and nothing is deleted) and the matching `AuditSoftwareIdentity`. `RunOnce(CancellationToken)` is its only operation: it purges the expired, unheld, complete UTC months of its own store under the retention policy that file declared at creation, oldest first, at most 240 months per run (`MoreExpiredMonthsRemain` says to run again). The caller chooses no month and no time (the store's own clock decides what has expired: month end plus the stored retention days), and cannot mint or hold a maintenance capability or reach hold release.

For each month the runner asks the store's internal authority for a fresh single-use capability bound to exactly that month, so every purge is audited by its authority receipt and its purge receipt, committed atomically with the deletion. A month with an active legal hold is `SkippedHeld`; a month with a row that fails verification is `FailedVerification` and left untouched without stopping the other months; a month the store refuses (a hold placed meanwhile, or purged by a concurrent run) is `Refused`. A disposed store or a cancelled token stops the run; months already purged stay purged. Concurrent appends continue throughout (each purge is one serialized store transaction), and two runners over the same file purge each month once. The runner does not schedule itself; the host composes and calls it. Offline tests cover the policy boundary to the second, held and unexpired months, owner and identity refusal, a corrupt month, per-month receipts, concurrent writers and runners, immutability through and after a run, the backlog bound, cancellation and a disposed store.

## Known limits and availability consequences

- **Retention runner exists; no host calls it yet.** `AuditRetentionRunner.RunOnce` is the public, narrow entry to policy-governed purge (see below). The purge, hold-release and capability entry points stay internal. No host composition root constructs or schedules the runner, so AU-11 is met by the mechanism and the runner proved offline against a real store, not by any running product; the PLT.57 composition (Design `delivery-graph` PLT.44 completion prerequisite) is where a composed configuration is proved.
- **Clock rollback after a purge.** Once a month has a retained purge receipt, an append stamped inside that month (the wall clock moved back by more than the retention window) is refused with `InvalidOperationException`, so an enforcement path that records before releasing a transfer fails closed until the clock moves on. This is an intentional availability trade-off in favour of the safe direction.
- **One corrupt row poisons its page and month.** Raw `INSERT` into the event table is not blocked (append semantics) and a person controlling the file can drop triggers. A row that fails verification (digest, owner, policy, partition, executor or closed event shape) makes every `Query` page containing it, and every purge of its month, throw `InvalidDataException`; there is no quarantine. This is fail-closed and consistent with the file not being tamper-proof.
- **Schema version.** `SchemaVersion` is 2 (event digest domain `event.v4`). A version 1 file is refused at open with no migration: no code outside this project and its tests constructs an audit store, so no version 1 file exists beyond test temporary files.
- **Real hosts not covered.** The egress and lease integrations are proved against the real `EgressAuthority` and `CapabilityLeaseManager` with test doubles for the classifier, allowlist, grant source and lease store; no host composition root passes `EgressAuditSink` or `CapabilityLeaseEventAuditSink` to a product yet.
- **Not covered.** No cross-process writer test (an in-process semaphore plus SQLite's write lock only), no Native AOT publish, no package pack in these tests (the package is packed and verified by the release pack job; PLT.46 owns its admission).

Offline tests exercise event completeness and round-trip integrity, owner scoping, ordinary SQL mutation refusal, inability of ordinary callers to obtain capabilities, wrong-store/policy/owner/action and expired capability refusal, expired/unexpired partitions, legal-hold enforcement/release, typed egress and lease intake shape/identity/fail-closed behavior, the real egress authority through the durable sink, durable non-signature authority and purge receipts, append serialization, and telemetry separation.
